If you know anything about me you know I love a book club, so you can imagine my excitement when I saw the Write the Docs Slack was starting a book club on Docs as Tests & AI by Manny Silva. I love yapping about books, doc accuracy is a crucial topic with the proliferation of AI, and the author is participating in the discussions – win, win, win! 

Going into the book I didn’t have a lot of context. At my last job we mostly manually tracked product changes. A tool like Doc Detective that could search at scale would have been incredibly helpful, especially when we introduced an AI chatbot into our forum. A chatbot does a great job at getting people the information they need quickly, but outdated or inaccurate information delivered confidently by the chatbot is not ideal at all. We had literally hundreds of guides to maintain and checking them manually for outdated information was a lot. 

The Intro does what it says on the tin – provides a brief intro to the topic, so if you haven’t read the author’s first book “Docs as Test” you won’t be lost. And much to my delight, there is a quickstart with some hands-on examples! I learn best by doing so I was eager to dive right in. I’ve completed coursework in using the command line and YAML, so I felt confident getting started. 

The first step was getting Doc Detective involved. ‘Easy enough,’ I thought. I entered the commands in the Terminal and…got an error. Took a little wind out of my sails, but a chance to troubleshoot feels like getting a taste of using the tool in a real situation. After a little detective work I discovered I needed to run the command as an admin. My command line coursework didn’t include this, so after a little reading about sudo I was good to go. I got my test YAML file created and saved and ran the command…and got an error. Oh well, I guess I get to do some more detective work. Terminal noted an error log, so off I went. It took a few minutes, but I eventually found the error code and error messages I needed to diagnose the problem, and, more importantly, a command to run to fix the error. A sudo command had caused a bit of a commotion in the cache and changing ownership cleared the issue up. I ran the Doc Detective test and…it passed! I know it was expected - and it’s a really small test - but I was stoked anyway!

The second test was to intentionally provoke a fail message. Seemed straightforward – put some text in the YAML file you know for sure isn’t on the target page. I spun up a new file as indicated in the book, ran the command, and…it passed? I was pretty sure that had to be a false positive, but just to be safe I changed the elementText to something I was absolutely, totally positive wouldn’t be on the target page – one of my cat’s nicknames. I entered the text, ran the command, and…it passed? At this point I was sure it was user (my) error, so I checked the file. Yep, the last line of my YAML file hadn’t been indented enough. D’oh! I thought I’d checked it, but it’s an easy thing to miss. I made the adjustment and ran the command…and it failed! Finally! The expected result!

Even though it took longer than I expected, and one of the obstacles was user error, I’m glad this played out the way it did. Having successfully run Doc Detective twice, for both passing and failing tests, I now had a much better concept of what the tool does and how it works. I have a concept of how it’s going to scale, but I can’t quite visualize it, so I’m looking forward to continuing with the book. Additionally, I think troubleshooting errors and/or mistakes is a very real world experience, so I’m always glad to add some troubleshooting experience to my arsenal. On to the next chapter – I’m curious to see how this scales.
